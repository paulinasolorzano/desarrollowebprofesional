2 ¿Qué es un CAPTCHA y por qué usarlo?
Definición

CAPTCHA son las siglas de Completely Automated Public Turing test to tell Computers and Humans Apart — una prueba automática para distinguir computadoras de humanos. Es el famoso "selecciona todas las imágenes con semáforos" o el widget de "No soy un robot".

Su función principal es bloquear bots y scripts automatizados que intentan acceder a sistemas sin ser humanos. En el contexto del login, previene los ataques de fuerza bruta — programas que prueban miles de combinaciones de usuario/contraseña por segundo.

¿Cómo funciona en el login?
El CAPTCHA agrega una pregunta antes del login. No revisa la contraseña: solo ayuda a confirmar que la petición viene de una persona y no de un script automático.
1
El usuario llena el formulario

Escribe su correo y contraseña. Antes de enviar, también debe completar el widget de hCaptcha.

2
hCaptcha entrega un token

Cuando la verificación se completa, hCaptcha genera un token temporal. Ese token no es una contraseña.

3
El frontend envía todo al backend

React manda correo, contraseña y captchaToken al login. El navegador no decide si el token es válido.

4
El backend valida y responde

Express verifica el token con hCaptcha. Si es válido, revisa las credenciales en la base de datos y responde el resultado.

Idea clave: hCaptcha ayuda a frenar bots; la base de datos sigue siendo la que permite o rechaza el acceso según el usuario y la contraseña.

3 hCaptcha vs reCAPTCHA: ¿cuál usaremos y por qué?

CAPTCHA es el concepto general. hCaptcha y reCAPTCHA son servicios concretos que implementan ese concepto.

Para esta práctica usaremos hCaptcha porque permite trabajar con claves de prueba públicas diseñadas para integración y pruebas. Así podemos concentrarnos en el flujo frontend → token → backend → verificación externa, no en la administración de una cuenta de proveedor.

Idea clave: lo importante no es memorizar una marca, sino entender el patrón: el usuario supera una verificación, el proveedor devuelve un token, el frontend lo envía y el backend lo valida.
Importante sobre desarrollo local: las claves de prueba de hCaptcha sí existen y son públicas, pero la documentación oficial advierte sobre el uso de localhost y 127.0.0.1 como hostname. Si el widget presenta problemas en desarrollo local, puede configurarse un hostname local, por ejemplo test.local, apuntando a 127.0.0.1 en el archivo hosts.
4 ¿Cuándo conviene usar CAPTCHA?

CAPTCHA es una medida anti-automatización. No sustituye una contraseña segura, 2FA ni el rate limiting. Su función es dificultar que un programa automatizado abuse de un formulario o endpoint.

Situación¿CAPTCHA?Motivo
Login expuesto a InternetPuede ser convenienteReduce intentos automatizados de fuerza bruta o credential stuffing
Registro público de cuentasSí, con frecuenciaEvita creación masiva de cuentas por bots
Recuperación de contraseñaFrecuentementeReduce abuso de correos/SMS y enumeración automatizada
Formulario público de contactoFrecuentementeReduce spam automatizado
Formulario interno después de iniciar sesiónNormalmente noAgregar CAPTCHA a cada operación deteriora la experiencia sin aportar suficiente valor
Acción sensible de alto riesgoCAPTCHA no bastaConviene combinar controles: autorización, 2FA, rate limiting, logs y reglas de negocio
Regla práctica: no se pone CAPTCHA “porque sí”. Primero identifica qué abuso automatizado quieres detener. Después decides si CAPTCHA es el control adecuado o si conviene combinarlo con rate limiting, 2FA u otras medidas.
5 ¿Cuándo se genera el token?

El token NO es el CAPTCHA. El CAPTCHA es el mecanismo de comprobación; el token es la evidencia temporal que el proveedor entrega cuando la verificación se completa correctamente.

En esta práctica, el token aparece en React mediante onVerify={token => setCaptcha(token)}. Después se envía al backend junto con el usuario y la contraseña.

Vida del token: es temporal y no debe tratarse como una contraseña permanente. La documentación de hCaptcha indica que los tokens deben verificarse en un periodo corto y que no deben reutilizarse.

7 Autenticación de 2 Factores — Fundamentos teóricos

La Autenticación de 2 Factores (2FA) agrega una segunda capa de verificación después del usuario y contraseña. Aunque alguien robe la contraseña de un usuario, necesita también el segundo factor para entrar — que generalmente es algo que el usuario tiene físicamente en su teléfono.

Esta sección es teórica — no se implementa en este proyecto porque requeriría modificar el flujo de login existente, agregar una columna a la BD y crear pantallas adicionales en el frontend. Se incluye para que conozcan la arquitectura antes de necesitarla en un proyecto profesional.

Los tres factores de autenticación
Factor 1 — Algo que sabes
Lo que ya tiene el sistema:
Usuario y contraseña. El usuario lo memoriza. Vulnerable si se roba o adivina.
Factor 2 — Algo que tienes
Lo que agrega 2FA:
Un código de 6 dígitos que cambia cada 30 segundos en la app del teléfono (Google Authenticator, Authy). Sin el teléfono, no hay acceso.
Factor 3 — Algo que eres
Biometría (no implementado):
Huella dactilar, reconocimiento facial. Requiere hardware específico. Se usa en apps bancarias móviles.
¿Cómo funciona 2FA con TOTP?

El estándar más usado se llama TOTP (Time-based One-Time Password). Funciona así:

1
Configuración inicial
El servidor genera un secreto único por usuario con la librería speakeasy. Se guarda en la BD encriptado.
2
Escaneo del QR
El secreto se convierte en un código QR con qrcode. El usuario lo escanea una sola vez con Google Authenticator.
3
Login en dos fases
Fase 1: usuario + contraseña. Si son correctos, el servidor pide el código de 6 dígitos de la app.
4
Verificación del código
speakeasy.totp.verify() confirma que el código coincide con el secreto del usuario en ese momento.

¿Por qué no se implementa en este proyecto? El flujo de login actual es un proceso de una sola fase: el usuario envía credenciales y recibe el JWT en una sola petición. El 2FA requiere dos fases — la primera verifica usuario+contraseña y devuelve un estado intermedio, y la segunda verifica el código TOTP y devuelve el JWT. Eso implicaría modificar el AuthContext, el LoginPage y toda la lógica de redirección que ya funciona correctamente. Para implementarlo bien, es un proyecto separado de 4–6 horas adicionales.

9 Preguntas de reflexión
  1. El middleware de CAPTCHA verifica el token con la API de hCaptcha desde el backend, no desde el frontend. ¿Por qué es importante que esa verificación ocurra en el servidor y no en el navegador?
  2. Las claves de prueba de hCaptcha siempre validan correctamente en localhost. ¿Qué riesgo representaría usar esas claves de prueba en un servidor de producción?
  3. Un atacante que quiera hacer fuerza bruta al login ya tiene el rate limiting de P11 que lo bloquea después de 10 intentos. ¿Para qué sirve el CAPTCHA si ya existe ese límite? ¿Se solapan o se complementan?
  4. En el diagrama de 2FA, el servidor devuelve un "estado intermedio" entre la fase 1 y la fase 2 del login. ¿Cómo podría implementarse ese estado intermedio en el sistema actual sin almacenarlo en la base de datos?
  5. ¿En qué tipo de sistema real considerarías implementar los tres mecanismos juntos: CAPTCHA + rate limiting + 2FA? Justifica con un ejemplo concreto.
  6. ¿Por qué el token no debe confundirse con el CAPTCHA? Describe quién genera el token y por qué el backend debe validarlo con el proveedor.
