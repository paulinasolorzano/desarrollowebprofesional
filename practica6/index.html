1 ¿Dónde estamos en el proyecto?

En las prácticas anteriores construimos el sistema completo de personas: base de datos, API REST, y frontend con CRUD y navegación entre pantallas. Sin embargo, hay un problema crítico: cualquier persona que conozca la URL de tu API puede leer, crear, editar o eliminar registros sin ningún control de acceso.

En esta práctica comenzamos la Fase 3 de seguridad. Agregaremos al backend un sistema de autenticación con JWT y bcrypt. Al terminar, solo los usuarios con una sesión válida podrán acceder a los endpoints de la API.

2 Conceptos clave: JWT, bcrypt y autenticación
🔐 ¿Qué es la autenticación y por qué la necesitamos?

Autenticación es el proceso de verificar que alguien es quien dice ser. En una aplicación web significa: el usuario presenta sus credenciales (usuario y contraseña), el servidor las verifica, y si son correctas le entrega un pase de acceso para usar el sistema.

Sin autenticación, cualquier persona que conozca la URL de tu API puede manipular todos los datos. Con autenticación, el servidor valida la identidad en cada petición antes de responder.

Analogía: Es como entrar a un edificio con guardia. Sin guardia cualquiera entra. Con guardia debes mostrar tu credencial — si es válida te dejan pasar. La credencial en este proyecto es el token JWT.
🎫 ¿Qué es JWT (JSON Web Token)?

JWT es un estándar para transmitir información de forma segura. Cuando el usuario inicia sesión correctamente, el servidor genera un token JWT y se lo envía. A partir de ese momento el frontend incluye ese token en cada petición para demostrar que está autenticado.

Un token JWT tiene tres partes separadas por puntos:

HEADER
Algoritmo de firma y tipo de token.
{ alg: "HS256", typ: "JWT" }
PAYLOAD
Datos del usuario: id, rol. No datos sensibles.
{ id: 1, rol: "admin" }
SIGNATURE
Firma digital que garantiza que nadie modificó el token. Solo el servidor puede verificarla.
Analogía: Un JWT es como un boleto de avión con código QR. Tiene tus datos (nombre, vuelo), un sello de autenticidad (la firma) y una fecha de expiración. El aeropuerto lo escanea en cada punto de control — si es válido pasas, si fue alterado o venció te detienen.
Importante: el payload del JWT no está cifrado — cualquiera puede decodificarlo. Lo que garantiza la seguridad es la firma: si alguien modifica el payload, la firma deja de ser válida y el servidor lo rechaza. Nunca pongas contraseñas u otros datos sensibles en el payload.
🔒 ¿Qué es bcrypt y por qué no guardamos contraseñas en texto plano?

Nunca debes guardar una contraseña tal como el usuario la escribe. Si alguien accede a tu base de datos, tendría todas las contraseñas expuestas. bcrypt convierte una contraseña en un texto completamente irreconocible llamado hash.

El proceso es unidireccional: puedes convertir una contraseña en hash, pero no puedes hacer el camino inverso. Para verificar si una contraseña es correcta, se vuelve a hashear y se compara con el hash guardado.

Analogía: Es como pasar carne por una picadora. Puedes hacer carne molida desde un filete, pero no puedes reconstruir el filete desde la carne molida. bcrypt hace lo mismo con las contraseñas.
¿Qué guardamos en la BD?Ejemplo¿Seguro si la BD se filtra?
Contraseña en texto plano ❌mi_password123No — cualquiera puede leerla directamente
Hash con bcrypt ✅$2b$10$xK8mN3vQ...Sí — es computacionalmente imposible revertirlo
🛡️ ¿Qué es un middleware de autenticación?

Un middleware en Express es una función que se ejecuta entre que llega la petición y que el controlador la procesa. El middleware de autenticación intercepta cada petición, extrae el token JWT del header, lo verifica, y solo si es válido permite que la petición llegue al controlador.

Si el token no existe, está expirado o fue alterado, el middleware responde directamente con 401 Unauthorized y la petición nunca llega al controlador.

Analogía: El middleware es el guardia en la puerta. Cada vez que alguien quiere entrar al controlador (la oficina), el guardia revisa su credencial (token). Si es válida lo deja pasar. Si no, lo detiene en la puerta — la oficina ni se entera de que alguien intentó entrar.

Paso 3Crear el controlador de autenticación auth.controller.js

Crea el archivo dentro de la carpeta controllers/. Contiene la lógica de las dos operaciones: registro (hashear contraseña y guardar usuario) y login (verificar credenciales y devolver token).

controllers/auth.controller.js — archivo nuevo

Analiza lo que hace cada función:

  • registro — recibe persona_id, usuario, password y rol. Hashea la contraseña con bcrypt.hash() usando 10 rondas de procesamiento y la guarda en la columna password_hash. La contraseña original nunca toca la base de datos.
  • login — busca al usuario por nombre. Si no existe responde 401. Si existe, usa bcrypt.compare() para comparar la contraseña enviada con el hash almacenado. Si coinciden, genera un JWT con jwt.sign() válido por 8 horas y lo devuelve.
💡 ¿Qué son las "10 rondas" de bcrypt? Indica cuántas veces bcrypt procesa internamente la contraseña antes de generar el hash. Más rondas = más seguro pero más lento. 10 es el estándar: tarda unos 100ms, suficiente para frenar ataques automatizados pero imperceptible para el usuario.

Paso 5Crear el middleware auth.middleware.js

Crea primero la carpeta middlewares/ dentro de backend/ (clic derecho → Nueva carpeta en VS Code). Luego crea el archivo dentro de ella. Este es el guardia que intercepta todas las peticiones a rutas protegidas:

middlewares/auth.middleware.js — archivo nuevo

El flujo del middleware paso a paso:

  • Lee el header Authorization de la petición. El frontend lo envía como Bearer eyJhbG...
  • Si no hay header, responde 401 — "no enviaste token".
  • Extrae el token separando por espacio y tomando la segunda parte (quita la palabra "Bearer").
  • Usa jwt.verify() con el mismo JWT_SECRET para verificar la firma del token.
  • Si el token es válido, guarda el payload en req.usuario y llama a next() para que la petición llegue al controlador.
  • Si el token es inválido o expiró, responde 401 — "token no válido".
💡 ¿Qué es req.usuario? Al agregar datos al objeto req en el middleware, esos datos quedan disponibles en el controlador. Así el controlador sabe quién hizo la petición (su id y rol) sin necesidad de volver a leer el token. En P07 lo usaremos para mostrar el nombre del usuario logueado en el Navbar.
