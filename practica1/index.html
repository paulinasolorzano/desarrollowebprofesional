1 Contexto del sistema a desarrollar

A lo largo de este curso construirás un Sistema Administrativo completo, funcional y seguro. No se trata de ejercicios aislados: cada práctica es un bloque que se conecta con las anteriores y prepara el terreno para las siguientes.

El sistema permitirá a una organización registrar personas, asignarles acceso con diferentes niveles de permisos, gestionar proyectos y controlar las tareas asociadas a cada uno.

Esta primera práctica es la base de todo: sin una base de datos bien diseñada, el resto del sistema no puede funcionar.

¿Qué módulos tendrá el sistema?
Módulo 1
Personas
Cualquier individuo de la organización. No necesariamente tiene acceso al sistema.

Campos: nombre correo puesto departamento activo
Módulo 2
Usuarios del sistema
Solo quienes necesitan iniciar sesión. Siempre vinculados a una persona.

Campos: usuario password_hash rol activo
Módulo 3
Proyectos
Proyectos con responsable, fechas, prioridad y estado de avance.

Campos: nombre fecha_inicio prioridad estado responsable_id
Módulo 4
Tareas
Tareas vinculadas a un proyecto y a una persona responsable.

Campos: titulo fecha_entrega prioridad estado proyecto_id
Importante: Una persona puede existir en el sistema sin tener acceso. Un coordinador, por ejemplo, puede ser responsable de proyectos sin necesidad de iniciar sesión.
2 Conceptos clave que debes conocer
¿Qué es una base de datos relacional?

Una base de datos relacional organiza la información en tablas (como hojas de cálculo), donde cada fila es un registro y cada columna es un atributo. Lo que hace especial a este tipo de base de datos es que las tablas pueden relacionarse entre sí mediante llaves.

Analogía: Imagina un archivo de expedientes en una empresa. Tienes un archivero de empleados y otro de proyectos. En cada proyecto hay una nota que dice "responsable: expediente #5". Eso es una relación: el proyecto apunta al empleado sin duplicar su información.
¿Qué es una llave primaria (PK) y una llave foránea (FK)?

La llave primaria (PRIMARY KEY) es un identificador único para cada registro en una tabla. No puede repetirse ni estar vacío. En nuestro sistema, el campo id de cada tabla es la llave primaria.

La llave foránea (FOREIGN KEY) es un campo que guarda el valor de la llave primaria de otra tabla, creando así la relación entre ambas. Por ejemplo, responsable_id en proyectos guarda el id de la tabla personas.

Analogía: La llave primaria es como el número de CURP de una persona: único e irrepetible. La llave foránea es como escribir ese número de CURP en un contrato para indicar quién es el firmante, sin tener que copiar todos sus datos.
¿Qué es la integridad referencial? (RESTRICT vs CASCADE)

La integridad referencial garantiza que las relaciones entre tablas sean siempre válidas. MySQL no te dejará crear un registro hijo que apunte a un padre inexistente.

ON DELETE RESTRICT: No permite borrar un registro padre si tiene hijos que dependen de él. Protege los datos históricos.

ON DELETE CASCADE: Si borras el registro padre, todos sus hijos se borran automáticamente.

Ejemplo en nuestro sistema: No puedes borrar una persona que tiene proyectos asignados (RESTRICT). Pero si borras un proyecto, sus tareas se eliminan solas porque no tienen sentido sin el proyecto (CASCADE).
¿Qué es el tipo ENUM?

ENUM es un tipo de dato que restringe los valores posibles de un campo a una lista predefinida. Si intentas insertar un valor que no está en la lista, MySQL lo rechaza automáticamente.

En nuestro sistema lo usamos para campos como rol ('admin', 'usuario', 'invitado'), prioridad ('baja', 'media', 'alta') y estado ('pendiente', 'en_progreso', 'completado').

¿Por qué no usar VARCHAR? Con VARCHAR alguien podría escribir "ADMINISTRADOR", "Admin" o "administrador" y serían tres valores distintos. ENUM garantiza consistencia: el valor siempre será exactamente uno de los permitidos.
¿Qué es el soft delete?

En lugar de eliminar físicamente un registro de la base de datos, el soft delete consiste en marcarlo como inactivo usando un campo booleano como activo = 0. El registro sigue existiendo pero el sistema lo trata como eliminado.

Esto es una práctica profesional que preserva el historial: si alguien fue responsable de un proyecto hace un año y después se "elimina" del sistema, los registros históricos siguen siendo válidos.

  • Verificar las relaciones entre tablas ejecutando consultas JOIN básicas.
