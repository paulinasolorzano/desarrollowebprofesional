2 Conceptos clave: JOIN triple y cambio de estado
🔗 ¿Qué es un JOIN triple?

En P09 uniste dos tablas: proyectos + personas. En P10 unes tres: tareas + proyectos + personas. Cada JOIN adicional agrega una tabla más a la consulta, usando la misma lógica de clave foránea.

La consulta SQL une las tres tablas en una sola llamada. El resultado es un objeto con datos de las tres tablas combinados, listo para mostrar en la tabla del frontend sin hacer peticiones adicionales.

Analogía: Es como pedir el historial médico de un paciente. El historial tiene el id del médico y el id del hospital. Con JOIN triple traes el nombre del médico y el nombre del hospital en una sola consulta, en lugar de hacer tres consultas separadas.
🔄 Cambio de estado sin recargar la página

Una de las ventajas de React es que puedes actualizar partes de la interfaz sin recargar la página completa. En este módulo, el alumno puede cambiar el estado de una tarea (de "pendiente" a "en_progreso", por ejemplo) directamente desde la tabla con un <select>.

Cuando cambia el select, se dispara una función que:

  1. Llama a PATCH /api/tareas/:id/estado con el nuevo valor
  2. El backend actualiza solo el campo estado en la BD
  3. React actualiza el estado local con setTareas — la tabla se re-renderiza instantáneamente
💡 ¿Por qué PATCH y no PUT? PUT reemplaza el recurso completo — necesitarías enviar todos los campos. PATCH modifica parcialmente — solo envías el campo que cambia. Es el verbo HTTP correcto para actualizaciones parciales como cambiar solo el estado.
🛡️ Permisos — mismo esquema que P09

Tareas sigue el mismo patrón de permisos que Personas y Proyectos desde P09:

💡 ¿Cómo funciona el cambio de estado sin recargar? Cuando el alumno cambia el select, handleCambiarEstado() llama al PATCH del backend. Cuando responde con 200, en lugar de volver a llamar a getTareas() (que haría otra petición completa), simplemente actualiza el arreglo en memoria con setTareas(prev => prev.map(...)) — cambia solo el objeto afectado y React re-renderiza solo esa fila.

7 Preguntas de reflexión
  1. En el JOIN triple, la consulta une tareas → proyectos → personas. ¿Por qué el orden importa? ¿Qué pasaría si intentaras hacer el JOIN en orden inverso (personas → proyectos → tareas)?
  2. ¿Por qué usamos PATCH para cambiar el estado en lugar de PUT? Da un ejemplo concreto de cuándo usarías cada uno en este proyecto.
  3. En TareasPage.jsx, cuando cambia el estado usamos setTareas(prev => prev.map(...)) en lugar de volver a llamar a getTareas(). ¿Cuál es la ventaja de ese enfoque? ¿Hay algún riesgo?
  4. Con P10 terminada, el sistema tiene 4 módulos CRUD. Si mañana el cliente pide agregar un módulo de Comentarios vinculado a tareas, ¿qué archivos tendrías que crear y cuáles modificar? Lista exactamente los nombres de archivo.
  5. La tabla de Tareas muestra el nombre del proyecto y del responsable gracias al JOIN. ¿Qué problema tendría el sistema si esos datos se obtuvieran con peticiones separadas (una por tarea) en lugar de JOIN?
