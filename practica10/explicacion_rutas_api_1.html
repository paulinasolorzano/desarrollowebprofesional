📌 Idea central: El cliente nunca va a la cocina directamente — siempre pasa por el mesero. De la misma forma, React nunca habla directamente con la base de datos — siempre pasa por los archivos *.api.js que a su vez llaman al backend.
2 Las rutas del backend — routes/*.routes.js

Las rutas del backend son instrucciones que le dicen a Express: "cuando llegue una petición HTTP con este método y esta URL, llama a esta función". Viven en el servidor — el usuario nunca las ve en el navegador.

⚙️ backend/routes/personas.routes.js
Cada línea define una puerta de entrada al servidor:
  • GET / → cuando alguien pide la lista de personas, llama a getAll()
  • GET /:id → cuando alguien pide una persona por id, llama a getById()
  • POST / → cuando alguien quiere crear una persona, llama a create()
  • PUT /:id → cuando alguien quiere editar, llama a update()
  • DELETE /:id → cuando alguien quiere eliminar, llama a remove()
backend/routes/personas.routes.js
¿Dónde viven? En el servidor Node.js que corre en el puerto 3000. El navegador nunca accede a estos archivos directamente — Express los ejecuta internamente cuando llega una petición HTTP.
3 Los archivos de API del frontend — api/*.api.js

Estos archivos viven en React (en el navegador) y su único trabajo es enviar peticiones HTTP al backend usando axios. Son el puente entre la pantalla y el servidor.

frontend/src/api/personas.api.js
¿Para qué sirve separarlo en un archivo aparte? Para no repetir la URL del backend en cada componente. Si mañana la URL cambia de /api/personas a /api/v2/personas, solo cambias una línea en personas.api.js — no en cada página de React que usa personas.

📌 Regla de oro: cada vez que en React llamas a una función de *.api.js, esa función envía una petición HTTP que viaja por internet (o por tu red local) hasta el servidor, donde una ruta del backend la recibe y la procesa. Los dos archivos (*.api.js y *.routes.js) siempre trabajan en pareja — uno en cada extremo de la misma conexión.
5 ¿Qué significa "consumir una API"?

Consumir una API significa que tu aplicación (el frontend) le pide datos o acciones a otro sistema (el backend) usando HTTP. Tú no tienes acceso directo a la base de datos desde React — le preguntas al servidor y él te responde.

❌ Sin consumir API
React accedería directamente a MySQL.
Cualquiera podría ver las credenciales
de la base de datos en el navegador.
No habría control de acceso ni roles.
Esto nunca se hace en producción.
✅ Consumiendo la API
React le pide los datos al backend.
El backend verifica JWT, roles y permisos.
Solo devuelve lo que el usuario puede ver.
Las credenciales de BD nunca salen del servidor.
Así funciona todo sistema web real.

6 Thunder Client — el mesero manual para pruebas

Thunder Client hace exactamente lo que hace *.api.js, pero de forma manual y visual. Lo usas para probar que el backend funciona bien antes de conectar el frontend.

Equivale a
crearPersona(datos) en personas.api.js
¿Por qué usamos Thunder Client si ya tenemos el frontend? Porque cuando algo falla, necesitas saber si el error está en el backend o en el frontend. Si Thunder Client responde bien, el problema es del frontend. Si Thunder Client también falla, el problema es del backend. Es la herramienta de diagnóstico del desarrollador.
