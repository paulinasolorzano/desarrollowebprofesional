2 Cookies httpOnly vs localStorage — por qué importa
⚠️ El problema de guardar el token en localStorage

Muchos tutoriales guardan el JWT en localStorage porque es simple. El problema es que localStorage es accesible desde cualquier JavaScript que corra en la página. Si tu aplicación tiene una vulnerabilidad XSS (Cross-Site Scripting) — donde un atacante logra ejecutar código JavaScript malicioso — ese código puede hacer esto:

Ataque XSS — lo que un script malicioso puede hacer con localStorage

Con una sola línea el atacante roba el token y puede hacerse pasar por el usuario en cualquier petición a la API.

🍪 ¿Qué es una cookie httpOnly y cómo protege el token?

Una cookie httpOnly es una cookie que el servidor crea con el atributo httpOnly: true. Esto le dice al navegador: "esta cookie es solo para ti — no la expongas a JavaScript". Aunque un atacante inyecte código malicioso en la página, document.cookie y cualquier otro método de JavaScript no pueden leer esa cookie.

Adicionalmente usamos dos atributos más:

Atributo¿Qué hace?
httpOnly: trueJavaScript no puede leer ni modificar la cookie. Solo viaja en las peticiones HTTP.
sameSite: 'strict'La cookie solo se envía en peticiones que originan del mismo sitio. Protege contra CSRF.
secure: trueLa cookie solo viaja por HTTPS. En desarrollo lo dejamos en false porque usamos HTTP local.
maxAgeTiempo de vida en segundos. Después de ese tiempo el navegador borra la cookie automáticamente.
Analogía: localStorage es como dejar tu llave de casa en el felpudo — cualquiera que pase puede tomarla. Una cookie httpOnly es como dejar la llave en una caja fuerte empotrada en la pared — el cartero (el navegador) la usa automáticamente para abrir la puerta, pero tú no puedes sacarla ni nadie más puede verla.
🔄 ¿Qué cambia en el código con cookies?
Con localStorage (antes)Con cookies httpOnly (ahora)
El backend devuelve el token en el body JSON: { token: "eyJ..." }El backend crea la cookie directamente con res.cookie(). No hay token en el JSON.
El frontend guarda el token: localStorage.setItem('token', ...)El frontend no hace nada — el navegador recibe y guarda la cookie automáticamente.
Axios agrega el header manualmente: Authorization: Bearer tokenEl navegador envía la cookie automáticamente. Axios solo necesita withCredentials: true.
El middleware lee el header AuthorizationEl middleware lee la cookie: req.cookies.token
Logout: localStorage.removeItem('token')Logout: el backend llama a res.clearCookie('token')
💡 ¿Por qué necesitamos withCredentials: true en axios? Por defecto el navegador no envía cookies en peticiones cross-origin (de localhost:5173 a localhost:3000). Con withCredentials: true le decimos que sí las incluya. El backend también debe tener CORS configurado con credentials: true y un origen específico (no *) para que esto funcione.
🌐 ¿Qué es la Context API de React?

La Context API crea un "almacén global" de datos al que cualquier componente puede acceder sin necesidad de pasarlo como prop. La usaremos para compartir el estado de sesión — si hay usuario activo, quién es, qué rol tiene — en toda la aplicación.

Analogía: La sesión del usuario es como la temperatura del edificio: todos los pisos la necesitan saber pero no tiene sentido que el piso 1 le diga al piso 5 cuánto hace. Con Context, hay un termostato central que todos consultan directamente.
🚪 ¿Qué es PrivateRoute?

PrivateRoute es un componente que tú creas para proteger rutas. Su lógica es simple: si hay usuario en el contexto, muestra el componente. Si no hay usuario, redirige a /login automáticamente. Se usa envolviendo las rutas privadas en App.jsx.

Paso 8Crear AuthContext.jsx — sin localStorage

Crea la carpeta src/context/ y dentro el archivo. La diferencia clave con el enfoque de localStorage: el estado usuario solo vive en memoria de React. La persistencia real la maneja la cookie del navegador. Al recargar, se hace una petición al backend para verificar si la cookie sigue siendo válida:

src/context/AuthContext.jsx — archivo nuevo
  • Al iniciar la app — useEffect llama a GET /api/auth/me. Si la cookie existe y es válida, el backend responde con los datos del usuario y se restaura la sesión. Si no hay cookie o expiró, el estado queda en null y PrivateRoute redirigirá al login.
  • login — llama al backend, que crea la cookie. Guarda los datos del usuario en estado.
  • logout — llama a POST /api/auth/logout para que el backend borre la cookie. Limpia el estado.
¿Por qué necesitamos el endpoint /api/auth/me? Porque al recargar la página React pierde todo su estado — no sabe si hay sesión. La cookie sigue ahí en el navegador, pero React no puede leerla (eso es precisamente lo que la hace segura). Para restaurar la sesión, le pregunta al backend: "¿esta cookie que te envío es válida? Si sí, dime quién es el usuario."
