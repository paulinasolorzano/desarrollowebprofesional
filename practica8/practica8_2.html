1 ¿Dónde estamos en el proyecto?

En las prácticas anteriores construiste el sistema completo para el módulo de Personas: base de datos, API REST, frontend con CRUD y navegación, y autenticación segura con JWT y cookies httpOnly. El sistema ya sabe quién eres cuando inicias sesión.

Lo que el sistema no sabe todavía es qué puedes hacer según tu rol. Un usuario administrador debería poder crear y eliminar cuentas, pero un usuario normal solo debería poder ver su propia información. En esta práctica implementamos esa lógica con el módulo de Usuarios y el sistema de roles.

2 Conceptos clave: roles, autenticación vs autorización y RBAC
🔑 Autenticación vs Autorización — dos cosas distintas

Son dos conceptos que muchos confunden porque van juntos, pero hacen cosas completamente diferentes:

ConceptoPregunta que responde¿Dónde lo implementaste?
Autenticación¿Eres quien dices ser?P06–P07: JWT + bcrypt + cookies
Autorización¿Tienes permiso para hacer esto?P08: middleware de roles (nuevo)
Analogía: La autenticación es mostrar tu credencial en la puerta del edificio — demuestras quién eres. La autorización es el sistema de tarjetas dentro del edificio — tu credencial abre algunas puertas pero no otras, dependiendo de tu nivel de acceso.
👥 Los tres roles del sistema

El sistema tiene tres roles con permisos distintos. Es importante entender qué puede hacer cada uno antes de escribir el código:

🛡️ ¿Qué es RBAC? (Role-Based Access Control)

RBAC significa Control de Acceso Basado en Roles. En lugar de dar permisos individuales a cada usuario, se asigna un rol y ese rol tiene permisos predefinidos. Es mucho más fácil de administrar: si quieres cambiar lo que puede hacer un administrador, cambias los permisos del rol, no los de cada usuario por separado.

En el código, RBAC se implementa con un middleware de autorización que lee el rol del usuario (que viene en el JWT) y lo compara con los roles permitidos para ese endpoint. Si el rol no está en la lista, responde 403 Forbidden.

Analogía: RBAC es como los permisos en una empresa. No le dices a cada empleado qué puede y qué no puede hacer. Defines los puestos (Director, Coordinador, Asistente) y cada puesto ya tiene sus permisos. Cuando contratas a alguien le asignas un puesto y automáticamente hereda todos sus permisos.
⚙️ ¿Cómo funciona el middleware de autorización?

Ya tienes el middleware verificarToken que comprueba que hay sesión activa. Ahora agregas un segundo middleware verificarRol que comprueba que el rol del usuario tiene permiso para esa acción concreta.

Los dos middlewares trabajan en cadena: primero pasa el filtro de autenticación (¿tienes sesión?) y luego el filtro de autorización (¿tu rol tiene permiso?). Solo si pasa los dos llega al controlador.

CapaMiddlewareSi falla responde
AutenticaciónverificarToken — ya existe de P07401 Unauthorized — no hay sesión
AutorizaciónverificarRol('admin') — nuevo en P08403 Forbidden — no tienes permiso
ControladorFunción que procesa la peticiónLa respuesta correcta
¿Por qué 401 y no 403? El código 401 significa "no sé quién eres" (no autenticado). El código 403 significa "sé quién eres pero no tienes permiso" (no autorizado). Son errores distintos y los clientes de la API los manejan de forma diferente.

5 Desarrollo paso a paso
Paso 1Crear el middleware de roles rol.middleware.js

Este es el nuevo middleware de autorización. Lo creas en la carpeta middlewares/ que ya existe. Funciona diferente al de autenticación: recibe los roles permitidos como parámetro y devuelve una función middleware.

backend/middlewares/rol.middleware.js — archivo nuevo

Observa algo importante en cómo está escrito: verificarRol('admin') es una función que devuelve otra función. Eso se llama factory de middlewares. Te permite escribir verificarRol('admin', 'usuario') para admitir varios roles con el mismo middleware.

💡 ¿Por qué usa req.usuario? Recuerdas que el middleware verificarToken guarda el payload del JWT en req.usuario. Ese payload tiene el campo rol. verificarRol simplemente lee ese campo — por eso siempre debe ir después de verificarToken en la cadena de middlewares.
Paso 2Crear el controlador usuarios.controller.js

Este controlador maneja las cinco operaciones del módulo de usuarios. La diferencia con personas.controller.js es que aquí también se gestiona el campo rol y se hace un JOIN con personas para mostrar el nombre del titular de cada cuenta.

backend/controllers/usuarios.controller.js — archivo nuevo

Puntos importantes de este controlador:

  • getAll — usa JOIN personas para traer el nombre de la persona vinculada a cada cuenta de usuario, no solo el persona_id.
  • create — llama a bcrypt.hash() exactamente igual que en P06. La contraseña nunca se guarda en texto plano.
  • update — actualiza solo los campos que llegan en el body. Si password viene en el body lo hashea; si no viene no lo toca.
  • remove — soft delete: cambia activo = 0 en lugar de borrar el registro.
¿Por qué no devolvemos el password_hash en getAll? El SELECT usa u.id, u.usuario, u.rol, u.activo, per.nombre AS persona — sin incluir password_hash. Nunca se envía información de contraseñas al frontend, aunque esté hasheada.
Paso 3Crear las rutas usuarios.routes.js con doble middleware

Aquí está la clave de P08: cada ruta tiene los dos middlewares en cadena. Primero verificarToken verifica que hay sesión, luego verificarRol verifica que el rol tiene permiso. Solo si pasa los dos llega al controlador.

✅ Esperado: 200 con arreglo de usuarios. Cada objeto incluye el campo persona con el nombre real.
Prueba 2 — Crear usuario nuevo
Thunder Client — POST http://localhost:3000/api/usuarios — Body JSON
✅ Esperado: 201. Verifica en phpMyAdmin que password_hash empieza con $2b$.
Prueba 3 — Editar rol de un usuario
Thunder Client — PUT http://localhost:3000/api/usuarios/2 — Body JSON
✅ Esperado: 200. El rol del usuario 2 cambia. La contraseña no se modifica porque no se envió en el body.
Prueba 4 — Acceso denegado con rol incorrecto

Inicia sesión con una cuenta de rol usuario (no admin). Con esa sesión intenta hacer GET a /api/usuarios.

✅ Esperado: 403 Forbidden con el mensaje "No tienes permiso para realizar esta acción". El servidor rechaza aunque haya sesión válida.
Prueba 5 — Desactivar usuario
Thunder Client — DELETE http://localhost:3000/api/usuarios/2 — sesión admin
✅ Esperado: 200. En phpMyAdmin el campo activo del usuario 2 es 0 pero el registro sigue existiendo.

7 Preguntas de reflexión
  1. ¿Cuál es la diferencia entre un error 401 Unauthorized y un 403 Forbidden? ¿En qué situación concreta del proyecto aparece cada uno?
  2. El middleware verificarRol siempre debe ir después de verificarToken en la cadena. ¿Por qué? ¿Qué pasaría si los pusieras en orden inverso?
  3. En el frontend ocultamos los botones de admin para los usuarios sin ese rol. Sin embargo, eso no es suficiente como medida de seguridad. ¿Por qué? ¿Qué es lo que realmente protege al sistema?
  4. ¿Por qué al editar un usuario el campo password es opcional? ¿Qué podría salir mal si siempre fuera obligatorio?
  5. Si un usuario con rol usuario intenta ver el perfil de otro usuario usando GET /api/usuarios/5, el endpoint actualmente lo permite (porque el rol usuario tiene acceso a ese endpoint). ¿Cómo modificarías el controlador para que un usuario solo pueda ver su propio perfil?
