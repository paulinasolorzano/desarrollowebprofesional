2 Conceptos clave
Helmet — headers HTTP de seguridad

Cuando Express responde una petición, incluye ciertos headers HTTP en la respuesta. Por defecto esos headers no tienen configuración de seguridad — exponen información del servidor y dejan al navegador sin instrucciones de protección.

Helmet es un paquete npm que agrega automáticamente 11 headers de seguridad en cada respuesta. No requiere configuración — con una sola línea el servidor ya los incluye.

Analogía: es como instalar rejas, cerrojo y alarma en una casa nueva. La casa funciona sin ellos, pero está expuesta. Helmet los instala todos de una vez sin que tengas que pensar cuáles poner.

Rate Limiting — límite de peticiones

Sin límite de peticiones, cualquier persona puede enviar miles de peticiones por segundo a la API — para adivinar contraseñas por fuerza bruta, saturar el servidor o extraer datos masivamente.

express-rate-limit cuenta las peticiones de cada IP y bloquea temporalmente cuando supera el límite definido. La respuesta es 429 Too Many Requests.

Se configura con dos límites distintos:

LímiteAplica aConfiguración
GlobalTodas las rutas100 peticiones por IP cada 15 minutos
EstrictoSolo /api/auth/login10 intentos por IP cada hora
Auditoría — trazabilidad de acciones

La auditoría registra quién hizo qué y cuándo en el sistema. Es una tabla en la BD donde cada acción importante (crear, editar, eliminar) deja una huella: el usuario que la ejecutó, la tabla afectada, el id del registro y la IP de origen.

En seguridad esto se llama trazabilidad — si algo sale mal puedes saber exactamente qué pasó, quién lo hizo y desde dónde.

OWASP Top 10 — las vulnerabilidades más críticas

OWASP (Open Web Application Security Project) publica cada año la lista de las 10 vulnerabilidades más frecuentes y peligrosas en aplicaciones web. En esta práctica verificarás cuáles de ellas ya están cubiertas por el sistema y cuáles quedan pendientes para producción real.

Se crean dos limitadores con distinto nivel de restricción. El global protege toda la API; el estricto protege específicamente el endpoint de login contra ataques de fuerza bruta.

backend/server.js — limiter global
backend/server.js — limiter estricto para auth
¿Por qué dos limitadores? El endpoint de login es el más vulnerable — un atacante puede intentar millones de combinaciones de usuario/contraseña. El límite de 10 intentos por hora hace ese ataque inviable en la práctica. El límite global de 100 peticiones en 15 minutos protege contra scraping y saturación general.

5 Checklist OWASP Top 10 aplicado al proyecto

Revisa cuáles de las vulnerabilidades más críticas ya están cubiertas por el Sistema Administrativo y cuáles quedarían pendientes para una versión de producción real.

A01 — Broken Access Control
Control de acceso roto
Cubierto
RBAC implementado desde P08. verificarToken + verificarRol bloquean accesos no autorizados. Invitado no puede modificar datos.
A02 — Cryptographic Failures
Fallos criptográficos
Cubierto
Contraseñas hasheadas con bcrypt (10 rondas). JWT firmado con HS256. Cookies httpOnly. Se recomienda HTTPS en producción.
A03 — Injection
Inyección SQL / XSS
Cubierto
Parámetros preparados (?) en todas las queries. Helmet agrega Content-Security-Policy para mitigar XSS. express-validator sanea entradas.
A04 — Insecure Design
Diseño inseguro
Cubierto
Arquitectura de capas: validación → autenticación → autorización → controlador. Principio de mínimo privilegio en roles. Separación frontend/backend.
A05 — Security Misconfiguration
Configuración insegura
Cubierto en P12
Helmet configura headers automáticamente. Variables sensibles en .env. CORS restringido a origen específico. Rate limiting activado.
A06 — Vulnerable Components
Componentes vulnerables
Parcial
Mantener dependencias actualizadas con npm audit. Para producción: revisar periódicamente con npm audit fix.
A07 — Auth Failures
Fallos de autenticación
Cubierto
Rate limit en login (10 intentos/hora) previene fuerza bruta. JWT con expiración. Cookies httpOnly y sameSite: strict.
A08 — Software Integrity
Integridad del software
Parcial
package-lock.json fija versiones exactas. Para producción: verificar integridad de paquetes con npm ci en lugar de npm install.
A09 — Logging Failures
Fallos de registro
Cubierto en P12
Tabla auditoria registra quién hizo qué y cuándo. errorHandler registra errores en consola. Para producción: usar un logger como Winston.
A10 — SSRF
Server-Side Request Forgery
No aplica aún
El sistema no hace peticiones a URLs externas en esta versión. Relevant si se agrega integración con servicios de terceros.
Resultado: el Sistema Administrativo cubre 7 de las 10 vulnerabilidades OWASP de forma completa y 3 de forma parcial. Para una versión de producción real, los puntos parciales requieren configuración adicional de infraestructura (HTTPS, logger externo, monitoreo de dependencias).

7 Preguntas de reflexión
  1. Helmet agrega el header X-Frame-Options: SAMEORIGIN. ¿Qué tipo de ataque previene ese header y cómo funciona ese ataque contra una aplicación web?
  2. ¿Por qué el rate limit de login es más estricto que el global? ¿Qué pasaría si ambos tuvieran el mismo límite de 100 peticiones por 15 minutos?
  3. La función registrarAuditoria() tiene un try/catch interno que solo hace console.error si falla. ¿Por qué no propagamos ese error con next(err)? ¿Qué consecuencia tendría si lo hiciéramos?
  4. El checklist muestra que A06 (Componentes Vulnerables) está parcialmente cubierto. ¿Qué comando usarías para revisar las vulnerabilidades actuales de las dependencias y cómo interpretarías el resultado?
  5. ¿Por qué .env nunca debe subirse a GitHub? Describe el escenario de ataque concreto que ocurriría si el JWT_SECRET quedara expuesto públicamente en un repositorio.
